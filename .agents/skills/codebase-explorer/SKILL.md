# Codebase Explorer Skill (V5)

## Overview

Generate architecture documentation for any codebase using a 4-phase pipeline. MCP Server handles all deterministic analysis (parsing, dependency graphs, token estimation). The Skill/Agent handles semantic understanding (reading code, writing documentation, reorganization).

## Two-Document Model

| Document | Purpose | Generated By |
|----------|---------|-------------|
| INDEX.md | Entry point: module map + Mermaid graph + per-module summaries | Phase 4 (assembled from DETAIL fragments) |
| DETAIL.md | Per-module: file-by-file analysis (功能/数据流/核心接口/依赖) | Phase 3 (parallel sub-agents) |

No OVERVIEW.md. No SNIPPET.md. All information lives in INDEX or DETAIL.

## 4-Phase Pipeline

### Phase 1: Analysis (Deterministic)
- Call `analyze_codebase(path, force_reindex=true)`
- MCP parses source, builds DAG, extracts feature cones, estimates tokens
- Output: 6 JSON files in `.codebase-analysis/`
- Call `get_modules(mode="summary")` to see module overview
- See [phase1-analysis.md](phases/phase1-analysis.md)

### Phase 2: Auto-Validation (No LLM)
- Rule-based checks on MCP output:
  - Cone size warnings (> 50k tokens)
  - Single-file cone flags
  - Coverage check (all files assigned to a module)
  - Field completeness (token_count, layers_within_cone, cohesion_score)
- See [phase2-validation.md](phases/phase2-validation.md)

### Phase 3: DETAIL Generation (Parallel)
- For each module, spawn a sub-agent:
  1. Call `get_modules(module_id=X)` to get file list + token counts
  2. Call `doc_operation("get_template")` for DETAIL format
  3. Call `doc_operation("get_protocol")` for the three-step protocol
  4. For each file: read source → write four sections → query `get_function_deps(file=X)`
  5. Write `<!-- index-fragment:{module_id} -->` block at end of DETAIL
- See [phase3-detail.md](phases/phase3-detail.md)

### Phase 4: INDEX Assembly + Reorganization
- Single agent with global view:
  1. Call `doc_operation("update_index")` to assemble INDEX from all DETAIL fragments
  2. Review module organization for semantic coherence
  3. Use `doc_operation("move_detail")` to reorganize if needed
  4. Re-run `doc_operation("update_index")` after any changes
- See [phase4-index.md](phases/phase4-index.md)

## 9 MCP Tools

| Tool | Phase | Purpose |
|------|-------|---------|
| analyze_codebase | 1 | Parse codebase, build graphs, extract cones |
| get_structure | 1-4 | Query file structure |
| get_modules | 2-4 | Module listing (summary) or detail (with files, tokens, deps) |
| get_dependency_graph | 3-4 | File-level dependency subgraph + Mermaid |
| get_function_deps | 3 | Cross-file function call dependencies |
| get_file_tokens | 3 | Token estimates per file |
| get_progress | any | Resume from checkpoint |
| submit_analysis | 3-4 | Persist progress for recovery |
| doc_operation | 3-4 | Template, protocol, INDEX assembly, block-level reorganization |

## Sub-Agent Usage Guide

Phase 3 sub-agent prompt MUST include:
- Target module's `module_id` and file list (from `get_modules`)
- DETAIL format template (from `doc_operation("get_template")`)
- Three-step protocol (from `doc_operation("get_protocol")`)
- Token budget upper limit
- Background: "MCP provides structural data only. YOU must read the source code and understand what it does."

## Context Compression Recovery

If context approaches limit:
1. Call `submit_analysis` to persist current progress
2. In new session: read SKILL.md + call `get_progress()` to restore state
3. Continue from incomplete tasks
