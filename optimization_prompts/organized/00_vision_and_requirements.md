# 需求愿景与设计思想

> 本文档从原始对话中提取用户的所有核心 Prompt，梳理需求全貌，并总结设计核心思想。

---

## 一、原始需求提取

以下按对话顺序，提取用户在交流中表达的每一个关键需求点。

### 1. 初始诊断需求

> "我之前按照这个计划，应该是完整的完成了实现，我进行了一些检查..."

用户完成了第一版实现后进行了 E2E 测试，发现虽然 18 个任务全部完成，但产出的文档存在链接断裂、内容空洞、覆盖率为零等问题。**触发了对整体设计的重新审视。**

### 2. 核心功能定义

> "整个流程的执行，应该是更多的交给 CLI Agent，我们需要实现的就是对这个代码化的代码文件，函数等结构的关系，还可以加上文件的占用 token 数量的计算（这个可能是新功能），以及代码之间模块深度的检测，避免在一个模块中包括针对过多代码的分析，导致整个架构出现问题。"

**核心需求**：

- MCP 负责代码的结构化分析（文件、函数、类、依赖关系）
- 新增 Token 数量估算功能
- 模块深度检测，防止单个模块过度膨胀
- 流程执行权交给 CLI Agent，MCP 只提供数据

### 3. 审查 Agent 机制

> "这个检测，可以不只是通过纯代码，而是应该再请一个 Agent 检查一下这个深度检测与模块分割是否合理，还可以再启动一个审查 Agent 再次审查是否合理是否还需要修改。"

**需求**：引入 LLM 审查环节，由 Agent 判断代码分析产出的模块分割和深度规划是否语义上合理，支持多轮审查。

### 4. 可变深度的树结构

> "另外这个深度，也可以是类似树结构一样，可以有深度较深的分支，也可以有些深度不深的部分。"

**需求**：文档树不是统一深度，而是像真实的树一样——复杂的分支可以很深，简单的部分保持浅层。深度应该由代码自身的复杂度和依赖关系自然决定。

### 5. 渐进式披露的文档结构

> "使用这些分析后的结果，让 CLI Agent 根据 Skill 的要求，可以并行的进行针对具体代码文件的阅读，然后说明代码功能，最终应该给每个模块给出一个 INDEX，这个随深度的增加而给出新的 INDEX 针对下方所有模块的内容给出渐进式披露的高层文档。"

**需求**：

- Agent 并行阅读代码，产出功能说明
- 每个层级都有 INDEX 文档，汇总其下所有子模块
- INDEX 是渐进式披露的——从顶层概览到底层细节，逐层展开

### 6. 子模块的 INDEX 链接规则

> "假如说一个模块的子模块的功能很多，它作为一个最小的等级，然后它的 INDEX 应该和它上一个层级的其他模块的具体实现文档放在一起，然后注意也要要求再上一级的文档的 INDEX 中提到这个子模块的 INDEX。"

**需求**：导航链不能断裂——父级 INDEX 必须链接到子级 INDEX，保证从任一层级都能向上/向下导航。

### 7. 功能关联性分析

> "如果说一个模块依赖了其他的文件，那么它们的功能天生上就是有连续性的，我们在给出具体的功能介绍的时候也还是应该倾向于将这些相同功能的代码尽量的放在一个模块，或者说需要在 DETAIL 的说明中至少提到这个互相之间的依赖关系。"

**需求**：

- 依赖关系是架构文档的灵魂，必须贯穿到最终文档中
- 功能相关的代码应归为同一模块
- 即使分属不同模块，也要在文档中明确标注依赖关系

### 8. 功能优先的组织原则

> "我希望确定一下...graph-sitter 应该是给出了这个代码库所有代码的，各个函数之间的使用情况，以及类的使用情况，这些信息，应该从语义来讲，可以找出来功能关联紧密的代码对吗？"

**核心确认**：用户希望利用 graph-sitter 提供的完整依赖信息（函数调用 + 类继承 + import），来自动发现功能上紧密关联的代码组。

### 9. 层级关系的表达

> "如果说遇到了一个功能的实现，可能底层较为复杂，然后后续可能使用这个功能的只有一个文件，然后使用这个文件的又有更多其他的功能，那么这样的一个关系是否能够得到体现呢？"

**需求**：文档要能清晰表达 **"宽→窄→深"的漏斗形依赖关系**：

- 底层复杂实现（深）
- 中间门面层（窄）
- 上层多个使用者（宽）

### 10. 功能与层级的融合

> "我们应该还是从功能出发，将不同的功能作为不同的分类；同时在这些不同的功能中，也要维持该功能所拥有的代码层级之间的这种关系。"

**这是用户最终确定的核心设计原则**：

- **第一维度：功能分类** — "这个代码库提供了哪些功能？"
- **第二维度：层级内嵌** — 每个功能内部保持从入口到实现的依赖链

### 11. 服务 Vibe Coding

> "我觉得在现在的 vibe coding 开发过程中，我们可能更多的还是会从功能的角度来进行 coding。所以更加方便于 AI 去检索代码，了解整个代码的逻辑。"

**使用场景**：文档的首要用户是 AI Agent（在 vibe coding 流程中）。组织方式要让 AI 能快速从功能需求定位到需要修改的代码文件。

### 12. 每步结果持久化

> "我希望这一部分的结果，每一步都应该有一个输出并保存下来，作为后续不管是用户查看，还是进一步让这个 CLI Agent 去完成后续任务的文档依据。"

**需求**：流水线每一步都产出持久化文件（JSON / Markdown），既供人阅读，也作为下一步的输入。支持断点恢复。

### 13. 信息分层避免重复

> "尽量避免出现重复，不要有过多重复的信息。"

**需求**：DETAIL 和 INDEX 之间要有清晰的信息边界，避免同一内容在多处重复。

### 14. 动态文档预算

> "我认为这个采用实际代码量以及这个比例（源码的 15-30%）是比较合理的，动态的进行管理。"

**需求**：文档 Token 预算不应固定，而是按源码量的 15-30% 动态分配（小模块 30%，大模块 15%，下限 800 上限 6000）。

## 二、需求全景图

综合以上所有需求点，整个系统要实现的功能可以概括为：

```
输入：一个代码库的路径
输出：一套按功能组织、渐进式披露的架构文档

流程：
  ┌─────────────────────────────────────────────────────┐
  │ MCP Server（确定性分析）                              │
  │   代码解析 → 加权依赖图 → SCC/DAG → 功能锥体提取     │
  │   → Token 估算 → 任务分配                            │
  │   → 输出 5 个 JSON 文件                              │
  └────────────────────┬────────────────────────────────┘
                       │
  ┌────────────────────▼────────────────────────────────┐
  │ 审查 Agent（语义验证）                                │
  │   检查分组/深度是否语义合理 → 调整建议                 │
  └────────────────────┬────────────────────────────────┘
                       │
  ┌────────────────────▼────────────────────────────────┐
  │ DETAIL Agent（并行，读源码）                          │
  │   阅读代码 → 理解功能 → 产出 DETAIL.md + SNIPPET.md  │
  └────────────────────┬────────────────────────────────┘
                       │
  ┌────────────────────▼────────────────────────────────┐
  │ INDEX Agent（不读源码）                               │
  │   架构数据 + SNIPPET → INDEX.md + OVERVIEW.md        │
  └─────────────────────────────────────────────────────┘

最终产物：
  .codebase-docs/
  ├── INDEX.md（全局架构概览 + Mermaid 图）
  ├── {功能A}/OVERVIEW.md + DETAIL.md
  ├── {功能B}/OVERVIEW.md + DETAIL.md
  ├── {基础设施}/OVERVIEW.md + DETAIL.md
  └── doc-index.json
```

### 用户画像与使用场景

| 用户                        | 场景                   | 期望                                     |
| --------------------------- | ---------------------- | ---------------------------------------- |
| AI Agent（Vibe Coding）     | "修改 CLI 行为"        | 从 INDEX → cli/OVERVIEW → 直接定位文件   |
| AI Agent（Vibe Coding）     | "请求上下文有 bug"     | 从 INDEX → request-handling → ctx/DETAIL |
| 开发者（新成员 Onboarding） | "整体架构是什么？"     | 读 INDEX.md 一页纸了解全貌               |
| 开发者（重构前）            | "改 app.py 影响什么？" | 通过依赖关系知道所有上层功能受影响       |

## 三、设计核心思想

### 思想 1：功能优先，层级内嵌

> 文档的顶层组织按**功能用途**分类（"这个代码库能做什么"），而非按文件树或抽象层级。每个功能内部，则按依赖链自然展示从入口到实现的层级关系。

这是与传统按目录/模块组织的根本区别。传统方式回答"代码在哪里"，功能优先回答"要改这个功能看哪里"——后者才是 AI Agent 在 vibe coding 中真正需要的答案。

### 思想 2：确定性分析 vs 语义理解 的职责分离

> MCP Server 做**确定性计算**（代码解析、图算法、Token 估算），Agent 做**语义理解**（阅读代码、撰写文档、审查合理性）。两者通过 JSON 文件传递数据，互不越界。

这解决了第一版的核心问题——把"应该由 LLM 做的事"（文档撰写）硬编码进了 MCP（Jinja2 模板），同时把"应该由 MCP 提供的纯数据"做得不够。

### 思想 3：架构信息是代码计算的常量，不是 Agent 发现的

> 依赖关系、功能分组、层级结构——这些都由代码分析预先确定，以 JSON 形式存在。Agent 不需要"发现"架构，只需要"理解"代码语义并填充到已确定的架构骨架中。

这保证了即使项目有百万行代码、任务被拆分给多个 Agent，架构的完整性也不会丢失。

### 思想 4：三种图算法各司其职

> - **SCC**（强连通分量）= 找出不可分割的最小功能单元
> - **DAG 分层** = 决定谁在上面谁在下面（纵向层级）
> - **Louvain** = 在同一层中区分不同功能组（横向分组，仅在扁平目录时作为 fallback）

三者缺一不可，但 Louvain 不再是主力，而是辅助工具。

### 思想 5：每步都有持久化输出，支持断点恢复

> 流水线的每一步都产出文件（`01_structure.json` → `05_task_manifest.json` → `DETAIL.md` → `INDEX.md`），任何一步失败都可以从上一步重新开始，不丢失已完成的工作。

### 思想 6：动态预算，按需分配

> 文档 Token 预算不是固定值，而是按源码量的 15-30% 动态分配。小模块不浪费空间，大模块不被截断。任务分配也是动态的——小功能合并批处理，大功能拆分子任务，确保每个 Agent 的上下文窗口不溢出。

---

## 四、一句话总结

**从代码的依赖关系中自动提取功能结构，用确定性分析划定骨架，用 LLM 填充语义，产出一套"功能优先、层级内嵌"的渐进式架构文档——让 AI Agent 在 vibe coding 中能从功能需求直接定位到需要修改的代码。**
